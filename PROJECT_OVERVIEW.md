# SolarOps — Solar Performance Intelligence

## 1. What Is SolarOps?

SolarOps is a solar performance intelligence system designed to understand, predict, and monitor the performance of solar power systems.

At its core, SolarOps uses machine learning to estimate how much electrical power a solar installation should produce under given environmental and operating conditions. It then compares that expected output with the actual power generated by the system.

The goal is to turn raw solar measurements into useful information that helps people understand system performance, identify unusual behaviour, and make better operational decisions.

In simple terms:

**SolarOps learns what normal solar performance looks like, predicts expected power generation, and highlights when actual performance differs from expectations.**

## 2. The Problem We Want to Solve

Solar installations are affected by several factors, including:

- Solar irradiance and available sunlight.
- Ambient and panel temperature.
- Wind and surrounding environmental conditions.
- Shading, soiling, and other environmental effects.
- Equipment condition and system operating behaviour.

Because these factors change over time, solar power generation is not constant.

Simply looking at actual power output does not always tell us whether a system is performing as expected. Lower production might be completely normal under cloudy conditions, while unexpectedly low production under favourable conditions could deserve further investigation.

SolarOps aims to address this problem by learning the relationship between operating conditions and solar power generation.

Instead of looking at power output in isolation, we want to understand it in context.

## 3. The Core Idea

The central concept behind SolarOps is **expected versus actual solar power generation**.

The system will:

1. Collect historical and operational solar measurements.
2. Understand the relationship between environmental conditions and electrical power generation.
3. Train machine learning models to predict expected AC power output.
4. Generate predictions using available system conditions.
5. Compare predicted output against actual measured output.
6. Identify significant differences and unusual performance patterns.
7. Present the results in a way that supports analysis and operational decisions.

For example, imagine a solar installation receiving strong sunlight. Based on its historical behaviour and current conditions, SolarOps estimates that it should produce a certain amount of AC power.

If the actual output is considerably lower than expected, SolarOps can flag that deviation for further investigation.

This does not automatically mean that the system has a faulty inverter, dirty panels, or shading. It means that actual behaviour differs from what the model expected, and the difference may deserve attention.

## 4. What We Are Building

SolarOps is intended to grow into an end-to-end machine learning product rather than remain a standalone notebook or model experiment.

The project is evolving through several stages. Stages 1–3 are complete; Stages 4–5 are in progress.

### Stage 1 — Data Understanding and Baseline ✅ Complete

We begin by understanding the available solar data, its quality, measurements, and relationships.

The first objective is to build a working baseline model that can estimate solar AC power output using relevant environmental and system measurements.

This gives us a measurable starting point and helps establish whether the available data contains useful predictive information.

**Delivered:** a cleaned 15-minute dataset (207,140 rows), a dummy baseline (196.2 kW MAE), and a linear regression baseline (38.8 kW MAE, R² 0.917).

### Stage 2 — Machine Learning Development ✅ Complete

Once the baseline is established, we improve the prediction system through experimentation and model development.

The objective is not simply to train a model with good results. We want to understand how well it generalizes to unseen time periods and how reliably it represents real solar system behaviour.

Over time, the model should become more reliable, reusable, and suitable for real-world predictions.

**Delivered:** v3 LightGBM with time features (25.7 kW MAE, R² 0.952). A v4 experiment with missing-value flags was evaluated but not adopted because it did not improve accuracy.

### Stage 3 — Prediction and Performance Analysis ✅ Complete

The trained model becomes part of a reusable prediction workflow.

Given new solar measurements, the system should be able to:

- Estimate expected AC power output.
- Compare predictions with actual measurements.
- Calculate performance deviations.
- Identify unusual behaviour.
- Provide useful information for further investigation.

The prediction and comparison process should work consistently without requiring someone to manually run a notebook.

**Delivered:** `models/v3.pkl` with versioned metadata, `src/solarops/predict.py` for safe prediction, trust labels (`ok`, `anomaly`, `unreliable_input`), and a dashboard data bridge.

### Stage 4 — Production-Ready ML System 🚧 In Progress

The project will gradually move beyond experimentation into a maintainable machine learning system.

This may include:

- Reusable data processing and prediction pipelines.
- Model versioning and persistence.
- Input validation and error handling.
- Automated testing and reproducibility.
- APIs for accessing model predictions.
- Model performance and data quality monitoring.
- Detection of changing data patterns and model degradation.
- Model updates and retraining when necessary.
- Deployment in an environment where the system can be used reliably.

The objective is to make the machine learning functionality usable outside the development environment.

**Done so far:** model persistence/versioning and input validation. **Next:** automated tests, an API, monitoring, retraining, and deployment.

### Stage 5 — SolarOps Application and User Experience 🚧 In Progress

Ultimately, SolarOps should provide a practical way to interact with solar performance intelligence.

The application could allow users to explore solar production, view expected versus actual output, understand performance trends, and investigate unusual deviations.

Potential capabilities include:

- Solar power generation dashboards.
- Expected versus actual output visualizations.
- Historical performance analysis.
- Performance deviation alerts.
- Environmental and operational insights.
- Reports that support maintenance and operational decisions.

The exact application design and feature set will evolve as the project develops.

**Delivered:** a 5-page Streamlit website in `app/` (Overview, Anomalies, Investigate, Predict, Model). The design and feature set continue to evolve.

## 5. Who Is SolarOps For?

SolarOps is intended to support people and organizations involved in operating, maintaining, and understanding solar power systems.

Potential users include:

- Solar plant operators.
- Solar system owners and managers.
- Renewable energy analysts.
- Maintenance and engineering teams.
- Organizations monitoring solar installations.

The main objective is to make solar performance information easier to understand and more useful for operational decisions.

## 6. What Makes This More Than a Prediction Model?

A model that predicts power output is only one part of SolarOps.

The broader goal is to build a complete system around that model.

A useful solar intelligence product needs to handle the journey from raw measurements to meaningful output:

**Solar Data → Data Processing → Machine Learning → Power Prediction → Performance Comparison → Insights → User Application**

It should also be possible to maintain, test, monitor, and improve the system after deployment.

We want the complete product to be useful beyond the environment in which the model was originally developed.

## 7. Long-Term Vision

The long-term vision is to develop SolarOps into a reliable solar performance intelligence platform.

It should help users understand how solar installations are performing, estimate expected power generation, recognize unexpected behaviour, and make more informed decisions using data.

As the project evolves, its capabilities may expand to support additional solar installations, more advanced performance analysis, and broader operational intelligence.

The focus remains on building something practical: a machine learning system connected to a real-world problem, with a clear purpose and a path toward actual usage.

## 8. Project Philosophy

SolarOps is being developed with a few important principles:

- **Practical over theoretical:** Build functionality that addresses a real solar performance problem.
- **Baseline first:** Establish a working model before introducing unnecessary complexity.
- **Data-driven decisions:** Base improvements and system behaviour on evidence from the data.
- **Production-minded development:** Consider reliability, testing, maintainability, and deployment throughout development.
- **Continuous improvement:** Treat the first model as a starting point, not the final solution.
- **Useful outcomes:** Focus on predictions and insights that can support real operational decisions.

---

**SolarOps is ultimately about turning solar data into actionable performance intelligence — from understanding what a solar system should produce to identifying when its actual performance tells a different story.**


## 9. Backend and Model Serving

SolarOps now includes a FastAPI backend in `apps/api/solarops_api/` that exposes the trained LightGBM v3 model through HTTP endpoints:

- `GET /health`
- `GET /model/info`
- `POST /predict`

The Streamlit dashboard in `apps/dashboard/` communicates with the backend over HTTP for prediction. Shared ML logic remains in `src/solarops/`.

Local development:

```bash
uv run uvicorn solarops_api.main:app --app-dir apps/api --reload
uv run streamlit run apps/dashboard/app.py
# or both:
uv run python scripts/dev.py
```

Tests:

```bash
uv run pytest
```
